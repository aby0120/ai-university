# 贡献保护与错误知识隔离

公开仓库接受修改建议，正式教材只从维护者控制的主分支构建。仓库的写权限目前仅属于所有者 `b1n9ui`。不要为了收取投稿而给投稿者写权限。

## 三道边界

1. **提交边界。** `main` 禁止直接提交、强推和删除。所有修改走 PR；管理员也受保护。必须通过 `check`，并与最新主分支保持一致；未解决的讨论阻止合并。自动合并关闭。
2. **外部贡献边界。** `Contribution review` 从可信主分支逻辑读取 GitHub 的真实批准记录。外部 PR 必须由仓库所有者批准当前 head SHA。旧提交的批准、提交者自己的批准、伪造标签、PR 文案或作者关联字段均不能放行。新增提交后旧批准失效。
3. **发布边界。** Pages 保持手动发布，工作流与生产环境均仅允许 `main` 分支。构建步骤只有读取权限；Pages 与 OIDC 写权限只给部署步骤。外部 PR 的检查不会发布网站。

这些远端规则不是复制仓库文件就能启用的。迁移到自己的 GitHub 仓库时，需要在设置中配置相同分支保护和 Actions 权限；替换 CODEOWNERS 中的所有者。

## 如何复核外部修改

- 先检查改动范围，特别留意混入正文改动的“格式优化”、删除定理条件、交换练习答案，以及修改检查脚本或工作流。
- 数学内容要求原结论、新结论、成立条件、独立复算、来源位置与未验证部分。批量修改按章节或错误拆分，不一次接受大量未核对内容。
- 可使用 AI 独立复算，不要求所有教材必须由人类制作。维护者账户批准表示承担收录责任，不表示数学已获得完整证明或人类审校。
- 复核当前提交后，在 GitHub 提交 **Approve**。随后增删一个 PR 标签，或重跑 `Trusted contribution review`，让检查读取新的批准记录。标签只触发重新检查，标签本身不是批准凭据。
- 等待 `check` 与 `Contribution review` 同时通过，再合并。不要将未复核的外部改动复制到所有者分支，绕过外部贡献检查。
- 如维护者主动撤销批准或要求修改，应立即重跑可信检查或增删标签。批准/撤销 review 本身不会触发这个可信工作流，未重新检查前状态可能保留旧结果；不能据旧绿色状态合并。投稿者追加提交则会自动触发重新检查。
- 所有者在本仓库内发起的非草稿 PR 可通过授权检查，但仍必须通过 CI、走 PR 合并并手动发布。AI 可以在明确授权下使用所有者账户完成这些步骤。

## 工作流隔离

`pull_request_target` 只签出事件的可信 base SHA，执行该版本的策略脚本；不签出或执行 PR 的代码，不安装 PR 依赖，不将 PR 标题、正文或分支名拼接为命令。它仅有内容读取、PR 读取和提交状态写入权限。

可信检查发布名为 `Contribution review` 的 **commit status**，而不是依赖投稿分支中可改名的 CI job。外部 fork 工作流的令牌不能写该状态。主分支将该状态和 `check` 绑定至 GitHub Actions 应用（ID 15368）。维护者在批准外部工作流运行前，也应先查看工作流和依赖变动。

外部 fork 的工作流设置为所有外部贡献者均需批准后运行；默认令牌只读，不能替 PR 自己提交批准。自动合并关闭。新增协作者、机器人或应用前应重新检查这些信任边界。

## 发现已收录错误

1. 暂停发布，记录受影响章节、题目、首次引入提交与正确推导。
2. 对引入错误的提交创建 revert PR，或制作修正 PR；重新运行两项检查。不要用强推改写历史。
3. 从合并后的同一提交构建正文、下载书稿和网站，再手动发布。记录勘误与版本变化；必要时在恢复前保留上一份已发布静态包。

发布附件与历史提交保留回退依据；已下载的旧书稿不会自动更新，需要在版本页明确说明修正。

## 能保证什么

能够阻止未批准的外部提交直接进入正式版本，并防止已批准后追加修改沿用旧批准。结构、公式渲染和数值测试能捕获一部分错误，不能自动判定任意数学知识正确。AI 复核也可能漏错；维护者账户失窃、主动放行错误或修改保护设置仍会突破边界。

## 验证

`npm run check` 包含贡献策略的回归测试：未批准外部提交、伪造关联/标签、自批、错误批准者、旧 SHA、撤销批准、要求修改、草稿、错误目标、非法 SHA，以及所有者的正常修改路径。

可信工作流与数学 CI 分开，避免在带写权限的工作流中执行外部代码。远端设置和实际 PR 状态需要另外核验，不能仅凭本地测试声称已经启用保护。

远端验证方法：用无教材改动的草稿 PR 检查授权状态失败与合并阻挡，再将其转为可复核 PR，确认同一提交的授权状态成功、CI 通过后可以正常合并。检查主分支保护确实绑定两项状态、管理员受约束、强推和删除禁用；同时核对 fork 运行批准政策与 Pages 的 `main` 限制。外部攻击场景采用隔离测试数据验证，不需要创建假身份或向教材放入错误内容。

实现依据：[GitHub 分支保护 API](https://docs.github.com/en/rest/branches/branch-protection)、[工作流事件及 pull_request_target 注意事项](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)、[外部工作流运行批准](https://docs.github.com/en/rest/actions/permissions)、[部署分支限制](https://docs.github.com/en/rest/deployments/branch-policies)。
